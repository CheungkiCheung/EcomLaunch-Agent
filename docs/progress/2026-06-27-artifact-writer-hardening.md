# 2026-06-27 - OpenSKU Artifact Writer Hardening

## Context

- Branch: `feature/ecom-launch-cockpit`
- Commit: working tree, not committed
- Goal: Make Phase 4 live validation stable through a real runtime artifact writer instead of relying on the model to emit large HTML/CSV/JSON payloads by hand.
- Scope: OpenSKU/EcomLaunch runtime tools, contract docs, live runner acceptance, and targeted backend tests.

## Thinking

The 900-second live run showed that timeout length was not the core problem. The run reached the production gateway/model path, invoked all five ecommerce specialist roles, avoided external search, and ended with run status `success`, but it failed acceptance because the model tried to write `launch-war-room.html` as a huge `write_file` payload and hit the model output token ceiling before the tool call materialized.

Prompt-only hardening had already failed twice: first on external search behavior, then on exact artifact contracts and finalization. The robust fix is to move deterministic artifact production into a runtime tool. The lead agent should still read data and synthesize a launch decision, but the formatting-sensitive contract work should be handled by code:

- JSON arrays/objects are written by Python JSON serialization.
- CSV files are written by `csv.DictWriter`.
- Markdown sections and exact labels are generated from templates.
- HTML is bounded and generated by the tool, so the model never has to emit a giant HTML tool-call payload.
- The same tool immediately runs the OpenSKU validator and returns `status=PASS|FAIL`.

Alternative rejected: ask the model to write smaller HTML chunks through `write_file`/append. That could reduce one failure mode, but it would still leave CSV schema, evidence id consistency, exact labels, and unsupported-claim safety to fragile prompt following.

## Live Validation Result

### Thinking

The first bundle-writer live run passed the artifact/tool acceptance criteria but exposed one final-response truthfulness issue: the chat response said `evidence-ledger.json` contained six evidence entries while the writer generated five. The artifact bundle itself was valid, but the final response is part of the user-facing contract, so this was not acceptable as the final Phase 4 proof.

I added two runner-level checks:

- `missing_final_response_requirements`: verifies stage, decision, next-loop test, promotion adjustment, data limitations, and all 10 artifact filenames appear in the final response.
- `final_response_consistency_errors`: verifies the final response does not claim artifact/internal counts that disagree with the generated files, currently including artifact count and `evidence-ledger.json` entry count.

The writer now returns `evidence_count=5`, and the skill/SOUL/manual prompt tells the agent not to claim row counts unless they were returned by a tool or read from the artifact.
